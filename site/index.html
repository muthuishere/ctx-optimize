A deterministic code knowledge graph for coding agents. query, card, change-plan, affected, path — every one returns a resolved symbol with its signature, its file:line and its callers. One static Go binary. No database, no server, no LLM, no embeddings, no MCP.

We're not the fastest to answer.
We're the one that answers. On the Linux kernel, CodeGraph beat us to the reply by 4.7× — and returned nothing useful on all five questions. The scoreboard below leads with our losses because that is the only way the wins mean anything.

grep wins the locate questions — 47% to our 42%. "Where is X" is exactly what a string search is for, and on a small, well-named Go router it beats a graph. The gap opens on "who calls this": 79% against 29%, because reverse call edges are a fact grep cannot produce at any speed.
And part of the gap is the model, not the tools. The judge and the agent are gpt-4o-mini — a cheap model that flounders on long grep transcripts. A stronger model would close some of this on its own. What the numbers show is a cheap agent lifted by structured answers, not a tool ceiling.

Symbol lookup — in the unreleased index work

Not in v0.12.0 yet. An exact-symbol index takes card <symbol> on the kernel from 1.73–1.83 s to 0.00–0.02 s. Fuzzy and ambiguous names are unchanged at ~7.4 s — deliberately, because they rank against every node in the graph. The index costs 0.43 GB, 20% of the graph; CodeGraph's index is 54% of their 4.1 GB store. Equivalence is verified, not assumed: 2,002 of 2,002 resolutions identical to a full scan.

how it works

Four decisions, and they are the whole product.

Tree-sitter, compiled to WASM

Real grammars, real ASTs — hosted by wazero inside the binary and fanned across every core. Zero setup: no toolchain, no language server, no runtime to install. 12 languages embedded; anything else is a one-command grammar pack.

Plain ndjson. No database.

The store is sorted, atomically written newline-delimited JSON — no SQLite, no Neo4j, no daemon. It diffs in git, greps in a pinch, and you can read it with your eyes.

Producer-scoped replace = incremental

Every node records which producer emitted it, so a re-gather replaces only that producer's slice and prunes what went stale. Re-sync after a change is sub-second, not a rebuild.

No LLM. No embeddings. No MCP.

The binary never calls a model and holds no credentials at rest. Same input, same graph, byte for byte. Your agent supplies the intelligence; the store supplies exact recall with file:line.

what you ask it

Five verbs. Each returns an answer, not a pointer.

verbthe question it answers
query "<terms>"Where is this? Ranked, complete hits under a budget — with the signature and file:line, not a list of paths to go open.
card <symbol>What is this symbol? Signature, doc comment, location, callers, callees — one shot, the read your agent no longer makes.
change-plan <symbol>I'm about to edit this. One composed answer: signature, callers, blast radius, and which tests to run — in place of a query → card → affected chain.
affected <symbol>What breaks if I change it? Reverse dependency walk across the whole graph.
path <a> <b>How are these two connected? The shortest chain of real edges between them.

Every edge carries its confidence: EXTRACTED is parsed fact, INFERRED is name-matched. Ambiguous calls are surfaced as a shortlist to grep — never guessed into the graph.

not just code

Your database, bucket, queue and API — in the same graph.

Nine native connectors. Point one at an environment variable name; the scheme in that variable's value picks the connector. Tables, buckets, topics and endpoints land as nodes beside your code, so one question spans all of it.

ctx-optimize add DATABASE_URL      # postgres://… → tables, columns, foreign keys
ctx-optimize add S3_ENDPOINT       # s3://…       → buckets and prefixes
ctx-optimize add KAFKA_BROKERS     # kafka://…    → topics and partitions
postgresmysqlmongodbrediskafkanatss3mssqlopenapi

Only the name ever appears on the command line or in committed config — never a raw URL. The value is read from the environment at dial time and is never stored in config, printed, or logged. Anything not on this list arrives through a drop-in adapter script and the validated JSON door. Sources, in the docs →

quick start

Four commands.

npm install -g @muthuishere/ctx-optimize       # one static binary per platform
ctx-optimize install --skills                   # one-time: teach your agent to use the store
cd your-repo && ctx-optimize up                 # bootstrap + gather (about a second)
ctx-optimize query "auth middleware"            # cited file:line answers, right now

macOS · Linux · Windows. Works with Claude Code, Codex, Copilot and Devin. up is idempotent — run it whenever; it bootstraps a bare repo, pulls a team store when the committed config declares one, and fast-refreshes a stale one. Everything else — monorepos, remotes, adapters, config keys — is in the docs.

what we don't claim

The claims we killed, and why they're not coming back.

Each of these was on this site or in our own docs at some point. Each was retired because a measurement said so — not because someone objected.

  • ×"Saves you tokens." Measured and killed. On frontier harnesses the store moved agent token usage by −0.2% on Claude Code and +3.0% on Codex — parity at equal quality. Agent fixed costs (system prompt, reasoning, the answer itself) don't shrink with a better tool. The record is in CRITIQUE.md, kept public on purpose. What did move in the graded run above is tool calls per run — 15.0 against 42.7.
  • ×"The fastest code graph." Retracted. CodeGraph answers kernel queries in 0.79 s to our 3.70 s and ripgrep in 1.59 s. We are the slowest tool in our own headline table. Speed is their column; answering is ours.
  • ×"Slower on every corpus" / any un-run head-to-head. potpie and Serena have no measured row here because we have not run them. A cell we did not measure stays empty rather than getting a plausible number.
  • ×"Fastest adapters." Never measured, so never claimed. What the native sources do is a capability: nine connectors, an env-var name on argv, and a secret value that is never read into config, stored, or printed.
Why publish this at all? Because the one thing we are asking you to believe — that a graph answers questions grep and a faster graph cannot — is only checkable if we also show the questions we failed and the columns we lose. The standing counter-weight to every value claim in this project lives in the repo: VISION.md and CRITIQUE.md.
